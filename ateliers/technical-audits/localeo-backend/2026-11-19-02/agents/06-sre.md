## SRE-01 — Le verrou de batch expire sans limiter la durée du handler

- **Statut : FORTEMENT ÉTAYÉ PAR LE CODE.** Domaine : exploitation / outbox / Live.
- **Localisation :** `app/application/exploitation/services/batchs.py:608-640` (`BatchRunner._acquire_lock`, `_release_lock`), `:642-700` (`execute`) ; `app/infrastructure/scheduler/http_client.py:51-63` (`BatchHttpClient.execute`).
- **Mécanisme et preuve :** le verrou est une ligne supprimable dès `expires_at <= now`, créée pour `timeout_seconds + 60`. Le handler est appelé directement à la ligne 669 ; aucun renouvellement ni arrêt à échéance n'entoure cet appel. Le timeout `requests` du scheduler borne son attente HTTP, pas le travail serveur synchrone. Le verrou peut donc devenir reprenable alors que le premier handler continue. La libération vérifie bien la corrélation : elle ne supprime pas le nouveau verrou, mais ne clôture pas l'ancien travail.
- **Flux/API concernés :** envois emails/SMS (`/protected/exploitation/{emails,sms}/batch/envoyer`), push Live (`app/api/localeo_live_api.py:1235-1338`, raccord batch `:1412-1415`), et tous les handlers utilisant ce runner. Exemple source : envois emails/SMS avec timeout batch de 300 s (`batchs.py:169-197`), lots séquentiels par défaut de 100, appels fournisseur de 20 s (`service_envoi_email.py:64-68`, `service_envoi_sms.py:48-52`). Push : boucle de notifications puis d'abonnements, sans budget global, malgré les claims et renouvellements individuels.
- **Conséquence/déclencheur :** si un handler dépasse son bail, une invocation ultérieure peut consommer une autre place HTTP/SQL simultanément ; amplification de contention et diagnostic ambigu entre timeout scheduler et traitement serveur encore actif. Les claims des messages protègent certains effets : ceci ne démontre pas un double envoi automatique. Un lot de 100 appels externes lents suffit conceptuellement à dépasser 360 s ; aucune fréquence observée n'est affirmée.
- **Confiance : élevée** sur l'absence de deadline/renouvellement générique ; moyenne sur la survenue réelle. Impact : élevé ; probabilité : moyenne conditionnelle aux fournisseurs lents et backlog ; criticité : **haute**.
- **Correction locale minimale :** ajouter un budget monotone aux boucles d'envoi et cesser de réclamer de nouvelles unités avant l'échéance ; pour les unités pouvant durer davantage, renouveler un bail propriétaire/version et vérifier sa validité avant les écritures finales. Conserver un mécanisme explicite d'incertitude fournisseur ; augmenter seulement le timeout ne résout pas la relation entre durée et bail.
- **Effort : M.** Risque : moyen (reprise/idempotence). Compatibilité : conserver contrats de réponse et claims existants ; pas de breaking change HTTP nécessaire. Transverse : exploitation, communications, Live ; ne pas généraliser une correction générique aux règles des tirages sans examen de leurs claims spécifiques.

## SRE-02 — Les envois génériques retiennent une connexion SQL pendant le réseau

- **Statut : FORTEMENT ÉTAYÉ PAR LE CODE.** Domaine : persistance / communications / capacité partagée.
- **Localisation :** `app/application/exploitation/use_cases/emails_batch.py:76-92` (`LancerBatchEmails.execute`) ; `sms_batch.py:60-67` (`LancerBatchSms.execute`) ; `app/infrastructure/persistence/repositories/repositories_sqlalchemy.py:1105-1112,1192-1195` (`obtenir_pour_envoi`) ; `app/infrastructure/persistence/db.py:33-44`.
- **Mécanisme et preuve :** après une première réservation committée, chaque message est rechargé sous `FOR UPDATE SKIP LOCKED`, puis `provider.envoyer` est appelé dans la même UoW, avant le commit de résultat. La connexion et le verrou restent détenus pendant l'appel externe. Les fournisseurs utilisent `requests` avec `timeout=20` ; ce délai n'est pas une mesure et n'est pas une deadline totale absolue. Les deux batchs utilisent le même `SessionLocal` que l'API, avec pool par processus de 5 + 5 et attente d'acquisition de 30 s par défaut.
- **Flux/API :** batches emails/SMS ; effets indirects possibles sur lectures Live, dashboard Animation et participation servis par le même processus et moteur SQL. Ce code générique ne décrit pas tout l'outbox moteur : le transport organisateur, notamment, libère explicitement l'UoW avant le réseau (`diffusion_messages_organisateur.py:43-68`).
- **Conséquence/déclencheur :** un fournisseur lent immobilise une connexion par envoi actif ; les overlaps de SRE-01 ou plusieurs batchs peuvent réduire la capacité SQL disponible pour les parcours publics. Deux batchs normaux ne saturent pas à eux seuls le pool par défaut : le constat porte sur le couplage et son amplification, pas une saturation établie.
- **Confiance : élevée** sur le mécanisme ; moyenne sur l'impact réel. Impact : élevé ; probabilité : moyenne conditionnelle ; criticité : **haute**.
- **Correction locale minimale :** transformer la réservation durable existante en protocole en trois temps : vérifier et committer la possession, envoyer hors transaction, finaliser par comparaison propriétaire/version. Préserver les barrières de révocation/conservation des emails d'accès ; une simple sortie du bloc UoW sans protocole équivalent serait incorrecte.
- **Effort : M.** Risque : élevé sur les emails d'accès et la remise incertaine ; compatibilité : pas de breaking change HTTP nécessaire. Transverse : identité/accès, conservation SaaS, communications et exploitation. Ne pas partager un second pool sans budget total PostgreSQL : cela déplace la concurrence plutôt que la supprimer.

## SRE-03 — Le pool scheduler unique peut retarder les clôtures derrière les transports lents

- **Statut : HYPOTHÈSE À VÉRIFIER.** Domaine : scheduler / budgets et dégradation.
- **Localisation :** `app/config.py:151` ; `app/infrastructure/scheduler/coordinator.py:110-136` (`_start_leader_scheduler`) ; `app/application/exploitation/services/batchs.py:365-419` (planifications) et `:78` (grâce par défaut).
- **Mécanisme et preuve :** tous les jobs partagent un seul exécuteur de quatre threads par défaut, chaque thread attendant un appel HTTP complet. `max_instances=1` s'applique à une planification, pas à une famille critique. Les clôtures vitrines/juste prix, tirages libres, CRM, campagnes, génération, transports et autres tâches tombent à la minute ; email/SMS/push se recoupent toutes les deux minutes. Pas d'exécuteur réservé aux clôtures ni de priorité dans cet enregistrement. Coalescence et grâce de 300 s limitent le rattrapage ; elles ne réservent pas de capacité.
- **Flux/API :** `/internal/animation-locale/{vitrines,juste-prix}/clotures/traiter`, `/internal/animation-locale/tirages-libres/traiter`, dépôt de campagnes et envois Live.
- **Conséquence/déclencheur :** plusieurs transports ou batchs durant plusieurs dizaines/centaines de secondes peuvent occuper les quatre places et différer les clôtures/résultats, voire provoquer des échéances manquées après la grâce. L'ordre exact et le retard réel exigent une observation ; aucune saturation n'est inférée du seul nombre de jobs.
- **Confiance : élevée** sur la topologie ; moyenne sur le scénario. Impact : élevé (retard des résultats) ; probabilité : indéterminée sans durées ; criticité : **moyenne, à qualifier**.
- **Correction locale minimale :** séparer exécuteurs de transport et opérations temporelles critiques avec capacités explicites, puis décaler les crons non critiques. Garder limites serveur et budget PostgreSQL globaux ; augmenter seulement les threads risque d'augmenter la pression sur l'API.
- **Effort : M.** Risque : moyen ; configuration source à documenter et tester ; aucun breaking change HTTP. Transverse : exploitation, communications, clôtures/résultats. Preuve complémentaire attendue : temps d'attente et d'exécution par job, événements missed/max-instances, occupation exécuteurs et âge des unités en attente, sur environnement jetable ou télémétrie autorisée.
