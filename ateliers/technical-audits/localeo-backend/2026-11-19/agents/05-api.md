# Audit indépendant — performance API

Première analyse finalisée le 19 novembre 2026, avant consultation de toute conclusion d’un autre agent. Backend lu directement au commit `7049e7fafc76f9119924f1082a5ee7457a175d85`, arbre applicatif propre lors du contrôle. Mission limitée aux chemins HTTP, traitements synchrones, dépendances externes et coûts de projection. Le catalogue et les flux de l’inventaire ont servi d’orientation ; chaque constat ci-dessous repose aussi sur une lecture des fichiers exécutables. Aucun import d’application, test, benchmark, accès base ou appel réseau n’a été effectué. Aucune configuration privée n’a été ouverte.

Trois anomalies majeures sont retenues. Leur mécanisme est **FORTEMENT ÉTAYÉ PAR LE CODE** ; aucune n’est **CONFIRMÉ PAR MESURE**. Leur importance réelle en exploitation reste à mesurer. Les observations secondaires et les protections qui évitent certains faux positifs figurent dans l’[annexe](05-api-annexe.md).

## API-01 — Le dashboard historique conserve un chemin global et répète ses lectures de détail

**Domaine :** API Animation, orchestration des lectures de pilotage. **Statut : FORTEMENT ÉTAYÉ PAR LE CODE. Confiance : élevée** sur le mécanisme, moyenne sur son poids en production.

**Entrées exposées et variante.** Le routeur `protected_router` possède le préfixe `/animation-locale` (`app/api/animation_locale_api.py:112`), puis `app/main.py:693` le monte sous `/protected`. L’entrée complète est donc `GET /protected/animation-locale/dashboard-performance`. Dans `consulter_dashboard_performance_animation`, lignes 3315–3346, `mode_lecture=borne` sélectionne explicitement un autre service. Quand le paramètre est absent, valeur par défaut, l’API appelle `ServicePilotageAnimation.dashboard` puis construit les résumés animation par animation. Les paramètres `actions_limit` et `actions_cursor` ne bornent que la branche explicite `borne`.

**Preuve et mécanisme.** Dans [pilotage_animation.py](../../../../../../localeo-backend/app/application/animation_locale/services/pilotage_animation.py#L101), `dashboard`, lignes 107–117, charge les animations de la commune et ses notifications, mais appelle aussi `uow.participants_animation.lister()` sans filtre, puis `uow.validations_animation.lister(date_debut=..., date_fin=...)` sans organisation. L’appartenance aux animations autorisées n’est appliquée qu’ensuite dans les listes Python. `ParticipantAnimationRepositorySqlAlchemy.lister`, `animation_locale_repositories.py:1343–1348`, termine par `.scalars().all()` et conversion de chaque entité. La lecture des validations fait de même, lignes 1510–1518. Même une requête ciblant une seule animation conserve donc le chargement initial de participants de toute la base. Une période réduit éventuellement les validations SQL, jamais le premier chargement des participants.

Le handler ajoute une deuxième phase : pour chaque animation retournée, `GestionAnimations.obtenir` puis `_animation_detail` sont appelés, `animation_locale_api.py:3336–3338`. Dans `_animation_detail`, lignes 1328–1347, la variante hors tombola recharge les participants et validations de cette animation pour calculer leurs nombres, ainsi que les notifications de la commune avant filtrage. La tombola bénéficie déjà de `charger_resumes`. Le découpage par cent des recommandations/réemploi, lignes 3340–3345, borne chaque lot d’enrichissement mais pas le nombre total d’animations ou les premières lectures.

**Conséquence et déclenchement.** Le temps de réponse, les conversions ORM et les allocations peuvent augmenter avec les participants d’autres organisations, puis avec le nombre d’animations locales. Le payload d’actions et les alertes sont également sans pagination sur cette branche. Plusieurs gestionnaires demandant ce bilan peuvent ainsi multiplier le travail. Cela décrit un risque de capacité et de latence ; le filtrage final observé ne constitue pas en lui-même une preuve de fuite de données. Aucun volume métier, nombre de requêtes effectif ou percentile n’a été mesuré.

**Bornes et alternative vérifiées.** `ServiceProductiviteAnimation.dashboard`, `productivite_animation.py:81–97`, dispose déjà d’une page d’actions et d’agrégats SQL. Son repository applique `limit + 1`, lignes 121–148, et borne les alertes à 50, ligne 289. Cette alternative évite de présenter toutes les variantes comme équivalentes. Le endpoint voisin `GET /protected/animation-locale/animations/{animation_id}/live`, handler lignes 3301–3305, reprend aussi une lecture complète des participants/validations dans `ServicePilotageAnimation.live:65–80`, bien que la réponse soit principalement des compteurs et annonce un intervalle de polling de 15 secondes. Il s’agit du même défaut de projection de lecture, avec un périmètre local plutôt que global.

**Correction minimale compatible.** Conserver la forme de réponse historique, mais produire ses compteurs et séries par agrégats filtrés sur les animations autorisées ; précharger les résumés nécessaires aux projections et les passer à `_animation_detail` via son paramètre `resume_batch`, déjà prévu. Reprendre ce principe pour les compteurs Live. Ne pas changer silencieusement le défaut en `borne` : les deux variantes ont des réponses différentes. Une migration explicite des consommateurs pourra être décidée séparément.

**Mesure disponible : aucune. Effort : M. Risque : moyen**, sur le périmètre temporel, les statuts et les compteurs affichés ; comparer les résultats à jeux identiques. **Breaking change : non** pour la correction proposée. Autres domaines affectés : persistance, mémoire, CPU, capacité des workers et expérience organisateur. Cause racine possible indépendante : conservation d’une ancienne composition de détail pour fabriquer des projections de liste. Le trafic exact des frontends n’est pas établi par cet audit.

## API-02 — Chaque lecture joueur réhydrate et redécode les médias privés, avec un budget qui ne coupe pas l’I/O

**Domaine :** API Live, contenu privé et stockage documentaire. **Statut : FORTEMENT ÉTAYÉ PAR LE CODE. Confiance : élevée** sur la chaîne, moyenne sur la sévérité opérationnelle.

**Entrée exposée.** `GET /public/localeo-live/participations/{participation_id}` correspond à `jeu_animation_api.py:75–87`, préfixe local `/localeo-live:26`, monté par `app/main.py:544` sous `/public`. Le Bearer est autorisé, puis `ServiceJeuAnimation.lire` reconstruit la projection personnelle. Les variantes sans illustration sélectionnée n’exécutent pas l’hydratation décrite ici ; les pages dédiées Juste Prix et vitrines sont distinctes.

**Preuve et mécanisme.** Dans [jeu_animation.py](../../../../../../localeo-backend/app/application/animation_locale/services/jeu_animation.py#L422), lignes 422–425, le service sélectionne uniquement les médias référencés par la projection autorisée et charge leur provenance. Après sortie de l’UoW, lignes 459–463, il appelle `hydrater_medias`. Cette séparation évite de retenir ici la transaction métier durant la lecture des images. `ServiceContenuGenerationAnimation.hydrater_medias`, `contenu_generation.py:368–395`, valide le périmètre et la provenance, puis lit chaque artefact séquentiellement, l’encode en base64 et appelle `_controler_media`.

Ce contrôle, lignes 300–317, décode à nouveau le base64, vérifie sa forme canonique, le SHA et les dimensions, puis utilise `DecodeurIllustrationWebp.decoder`. L’adaptateur `decodage_illustration.py:10–29` ouvre l’image et appelle `illustration.load()`. Les lectures successives d’un même contenu immuable reprennent donc récupération binaire, contrôles et décodage complet. La composition `service_jeu_animation`, `composition.py:58–66`, construit les adaptateurs et ne prévoit pas de cache de ces résultats.

Le budget par défaut est de 30 secondes (`contenu_generation.py:177–183`). Il est vérifié avant chaque média et après la boucle, mais `lire_brut:335–343` appelle directement le stockage. En mode S3, `S3DocumentStorage.get`, `document_storage.py:104–109`, effectue `get_object` puis `response['Body'].read()` ; la construction du client, lignes 83–89, ne transmet pas de budget restant. Le contrôle global ne peut donc interrompre un appel bloqué au moment exact où ses 30 secondes expirent. Les délais propres au SDK existent potentiellement, mais leur valeur effective n’a pas été lue dans un runtime ni mesurée : il serait incorrect d’affirmer une attente infinie.

**Conséquence et déclenchement.** Avec un stockage distant lent, une consultation joueur attend les lectures séquentielles nécessaires avant de rendre le JSON ; une illustration défaillante peut faire échouer l’ensemble. Avec de nombreux participants sur une même animation, les mêmes médias sont récupérés et décodés plusieurs fois. Un fichier local évite la dépendance réseau mais conserve le travail de contrôle et de sérialisation. Le coût devient sensible selon les latences du fournisseur, le nombre de médias sélectionnés et la simultanéité ; aucune de ces distributions n’a été observée.

**Protections vérifiées.** Les médias sont limités à 44 000 octets binaires, 60 000 octets pour l’objet média, WebP statique et trois dimensions autorisées. `borner_projection`, `projections_jeu.py:196–199`, refuse un document supérieur à 256 000 octets ; le service estime aussi le budget de projection en amont. L’API applique des gardes de lecture avant et après autorisation. Le constat n’est donc ni un payload sans limite ni une absence de contrôle de fréquence. Ces bornes limitent le volume unitaire, sans supprimer la répétition des appels et des décodages entre participants autorisés.

**Correction minimale compatible.** Ajouter un cache privé strictement borné, indexé par organisation, document et SHA, contenant les octets ou la représentation validée après vérification complète. Continuer à autoriser chaque lecture et à vérifier la correspondance de provenance avant d’utiliser le cache. Transmettre le budget restant à l’adaptateur réseau et définir explicitement délais de connexion, lecture et tentatives ; ne pas présenter la seule vérification d’horloge comme une échéance dure. Le JSON existant peut rester identique : une nouvelle API de médias n’est pas nécessaire pour ce premier correctif.

**Mesure disponible : aucune. Effort : M. Risque : moyen**, notamment séparation des organisations, révocation d’accès, invalidation et mémoire du cache. **Breaking change : non.** Autres domaines : CPU, mémoire, concurrence des threads, SRE et disponibilité du stockage. Cause racine possible indépendante : réemploi d’un validateur d’import complet pour chaque lecture de contenu déjà persisté et immuable. Les contrôles d’intégrité ne doivent pas être simplement supprimés.

## API-03 — Le retour de paiement appelle Stripe pour une vérification de métadonnées, sous une UoW SQL ouverte

**Domaine :** consultation d’achat Coffrets, intégration Stripe. **Statut : FORTEMENT ÉTAYÉ PAR LE CODE. Confiance : élevée.**

**Entrée et condition précise.** `GET /public/gestion-achats/paiements/retour/{achat_id}` est déclaré dans [paiements_api.py:34–41](../../../../../../localeo-backend/app/api/paiements_api.py#L34), routeur local `/gestion-achats/paiements` (ligne 13), montage `/public` dans `app/main.py:550`. Il exige le token de retour et accepte `X-Checkout-Session`. Le chemin sans cet en-tête ne contacte pas Stripe dans le use case observé.

**Preuve et mécanisme.** [ConsulterRetourPaiement.execute](../../../../../../localeo-backend/app/application/gestion_achats/use_cases/consulter_retour_paiement.py#L11), lignes 11–20, ouvre l’UoW, charge l’achat et vérifie le token. Si une session est fournie, il appelle immédiatement `recuperer_session_checkout`, puis utilise seulement `session.metadata['achat_id']` pour vérifier la concordance. Il lit ensuite coffret et résumé, et retourne le statut d’achat local. Aucun branchement n’évite l’appel distant lorsqu’un paiement est déjà confirmé.

`PaiementGateway.recuperer_session_checkout`, `paiement_gateway.py:226–232`, demande pourtant l’expansion `payment_intent`, `payment_intent.latest_charge` et `customer`. Ces expansions sont utiles à d’autres usages de cette méthode, mais ne sont pas consommées par cette lecture de retour. Le même helper construit ailleurs un événement de réconciliation : il faut donc distinguer ses consommateurs avant de modifier son comportement global.

Le contexte SQL demeure ouvert durant la requête Stripe, après le premier accès base et jusqu’au retour de `execute`. L’UoW ne ferme la session que dans `sqlalchemy_unit_of_work.py:216–219`. Cette structure peut retenir une connexion SQL pendant une attente de fournisseur qui n’a pas besoin de la transaction SQL. Aucun client Stripe ou délai explicite n’est configuré dans ces gateways ni dans les fichiers de configuration applicative examinés ; les politiques exactes du SDK déployé ne sont pas prouvées ici.

**Conséquence et protections.** Un achat localement confirmé peut voir sa page de retour ralentie ou indisponible à cause de Stripe, uniquement pour revérifier une métadonnée. Des actualisations répétées reprennent l’appel et les expansions. Le token de retour est vérifié avant l’appel : il ne s’agit pas d’un accès public arbitraire sans contrôle. Le statut affiché demeure volontairement celui de la transaction webhook locale ; la correction ne doit ni lui substituer le redirect ni supprimer le contrôle de correspondance de session.

**Correction minimale compatible.** Introduire une lecture Stripe minimale de métadonnées pour ce use case, sans expansions, avec budget réseau explicite. Charger et autoriser l’achat dans une UoW courte, effectuer la vérification distante après fermeture, puis relire l’état local dans une seconde UoW courte pour la réponse. Un petit cache borné de correspondance validée achat/session peut être envisagé ensuite, sans mettre en cache le statut financier. Cela conserve le contrat HTTP et les deux contrôles d’accès.

**Mesure disponible : aucune. Effort : M. Risque : moyen**, sur la cohérence du statut pendant la séparation des lectures et l’accès à une session incompatible. **Breaking change : non.** Autres domaines : persistance et pool SQL, concurrence, disponibilité externe et expérience d’achat. Cause racine possible indépendante : helper Stripe partagé entre réconciliation financière et consultation légère. Aucun gain de latence, débit ou taille de payload fournisseur n’est annoncé sans mesure.
